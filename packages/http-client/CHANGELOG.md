# @mokei/http-client

## 0.16.0

### Minor Changes

- Per-tool OAuth scopes with step-up. `createTool({ scopes })` (and `GenericToolDefinition.scopes`) declares the scopes a tool needs on top of the server-wide ones. They are never listed in `tools/list`. `ContextServer.requiredScopes(request)` reports them for a `tools/call`. `ContextServer` rejects a call whose auth lacks them with `INVALID_REQUEST` and `data: { error: 'insufficient_scope', scopes }`; without auth, scopes are not enforced. The HTTP handler answers such a call before dispatch with `403` and `WWW-Authenticate: Bearer error="insufficient_scope", scope=…, resource_metadata=…`, on both `2025-11-25` sessions and `2026-07-28` stateless requests. It reads the tool from the parsed body, never from the `Mcp-Method`/`Mcp-Name` headers. New: `HTTPHandlerParams.oauth` (`resourceMetadataURL`, `requiredScopes`, filled in by `mcpPlugin`), `runStatelessExchange`'s `authorize` hook and `insufficientScopeResponse`. The client OAuth middleware steps up on that `403`: it re-authorises for the configured, held and challenged scopes, stores the token under the same key with the new `StoredTokens.requestedScopes`, and retries once. Refreshes and re-authorisations keep the wider scopes, a 401 challenge's `scope` joins the authorisation request, and `stepUp: false` opts out. `parseBearerChallenge` is exported.

- OAuth hardening. `2025-11-25` HTTP sessions are now bound to the issuer and subject that sent `initialize`: a request from any other identity naming the session (POST, GET or DELETE) gets the same 404 as an unknown session. Session handlers receive each request's own auth through the new `ContextServer` `resolveAuth` param, which `createServer` now receives alongside `auth`. `request.auth` is a `RequestAuth` that adds `expiresAt` and `claims` (the verifier's decoded claims, surfaced from `AuthInfo.raw`). On the client, a generic `KeyValueStore<V>` (`get`, `set`, `delete`, `keys`, atomic `update`) is exported with `createMemoryStore` and, in `@mokei/host-node`, `createJSONFileStore`, whose writes are locked across processes. `TokenStore` is now `KeyValueStore<StoredTokens>`. **Breaking:** `TokenStore.clear` is renamed `delete`, and `update` and `keys` are required. Tokens are keyed by `tokenStoreKey({ resource, clientID, scopes })`, so existing stored tokens are ignored and each user signs in once. Middlewares sharing a store share in-flight refreshes and sign-ins, refreshes run inside `store.update` (so processes sharing a tokens file redeem a rotating refresh token once), and sign-ins through one handler run one at a time.

- OS keychain token store and `mokei auth`. `@mokei/host-node` adds `createKeychainStore<V>`, a `KeyValueStore` in the OS keychain through `@napi-rs/keyring` (loaded on first use; a `KeychainBackend` can be injected), and `createKeychainTokenStore()` for OAuth tokens under the `mokei-oauth` service. The keychain has no locking, so writes hold a lock file in mokei's state directory. The JSON file store and the keychain store now both lock with `@sozai/lock`, replacing mokei's own heartbeat lock. A holder whose process is provably alive is never taken over, and `staleLockMs` (default now 60000) applies only when the holder's liveness cannot be proven. An older mokei sharing a tokens file may still take over a lock this version holds for more than its 10-second heartbeat window. A missing or inaccessible keychain fails with `KeychainUnavailableError`. `createNodeOAuthMiddleware` takes `keychain`, mutually exclusive with `tokensPath`, and the CLI's `/context add-http` takes `--oauth-keychain`. Persistence stays opt-in. `@mokei/http-client` adds `revokeTokens` (RFC 7009: refresh token first, then access token; `unsupported_token_type` is skipped) and exports `canonicalResource`. AS metadata now reads `revocation_endpoint`, and an empty OAuth response body parses as `{}`. New CLI commands: `mokei auth list` shows stored sign-ins (never tokens), and `mokei auth logout <resource>` revokes, then deletes, every sign-in for a resource. It deletes even when revocation fails, exiting `1`. Both take `--keychain` or `--tokens <path>`, and logout also takes `--client-id` and `--no-revoke`.

- Move to enkaku 0.23, kokuin 0.7, `@teikyo/oauth` 0.3 and `@hozon/adapter` 0.3. A host must use the same lines. Kokuin 0.7 signing takes `identity.signToken({ payload })`.

### Patch Changes

- OAuth scope follow-ons and SEP-2243 header validation. Prompts (`createPrompt({ scopes })`) and resources (`ResourceDefinitions.scopes`, a list or a synchronous function of the URI) can require scopes, enforced on `prompts/get` and `resources/read` exactly like tool scopes, including the HTTP `403 insufficient_scope` and client step-up. `ContextServer.requiredScopes` covers all three. `tools/list` and `prompts/list` now advertise scopes under `_meta['dev.mokei/scopes']` (`SCOPES_META_KEY`). They are not filtered by the caller's scopes. **Breaking:** on `2026-07-28` the HTTP server now validates the SEP-2243 standard request headers against the body. A request must carry `MCP-Protocol-Version` and `Mcp-Method`, plus `Mcp-Name` on `tools/call`, `prompts/get`, `resources/read` and `tasks/get|update|cancel`, and every header must agree with the body. A missing or disagreeing header is rejected with `400` and JSON-RPC `-32020` (`data.mismatch: { header, body }`), which also replaces the old plain-text `400` for a version mismatch. `@mokei/http-client` already sends these headers. Hand-built requests must add them. `validateStandardHeaders` and `decodeHeaderValue` are exported from `@mokei/http-server`, and `MCP_NAME_HEADER_SOURCE` from `@mokei/context-protocol`, which `@mokei/http-client` now reads too.

- SEP-2243 `Mcp-Param-*` validation on the server. On a `2026-07-28` `tools/call`, the HTTP server checks each `Mcp-Param-{Name}` header against the arguments the tool's `x-mcp-header` annotations name. An absent or `null` argument needs no header, numbers compare numerically, and tools with invalid annotations are skipped. A missing, badly encoded or different header is rejected with `400` and `-32020`, and `data.mismatch.header` names the `Mcp-Param-*` header. This runs before the scope check. New: `validateParamHeaders` (`@mokei/http-server`) and `ContextServer.toolInputSchema(name)`. `collectHeaderAnnotations`, `isValidHeaderParamName` and their types move to `@mokei/context-protocol`, and `@mokei/http-client` still re-exports them. Fix: the client's stale-schema refresh now reads a `tools/list` answer sent over SSE. Before, it only accepted JSON, so the refresh-and-retry never worked against a stateless mokei server.

- Updated dependencies:
  - @mokei/context-client@0.16.0
  - @mokei/context-protocol@0.16.0
  - @mokei/logger@0.16.0

## 0.15.0

### Minor Changes

- Server OAuth exports removed in favour of `@teikyo/oauth`. `serveHTTP` is async, returns a `@sozai/http-server` `HTTPServer` (use `server.url`), answers `503` for verifier outages, and derives protected resource metadata from `auth.resource` (`auth.resourceMetadataURL` removed). Add `mcpPlugin` and `HTTPHandler.shutdown()`. JWKS and metadata fetch failures return 500 instead of 401. The OAuth client clears tokens and re-authorises on `invalid_grant`.

- Add the MCP Tasks extension for 2026-07-28: durable server tasks, task input and cancellation, authorised subscriptions, automatic client waiting, HTTP routing. Task input history persists in `TaskRecord.inputs`; withdrawn requests reject with `InputRequestWithdrawnError` and identical `requestInput` replays settle outcomes. `TaskManager.update` rejects non-outstanding keys with -32602. Add MRTR (SEP-2322) fixes: typed `allowInputRequired`, empty `inputRequests` rejected, exported `defaultMintRequestState`.

- Breaking: error classes and positional constructors take a single params object (`new TokenVerificationError({ code, message })`, `ProxyHost({ client })`) with read-only getters and exported `<ClassName>Params` types. `ContextHost` drops `_contexts`, `_localTools`, `_events`, `_dispose`; use `contexts`, `localTools`, `events` and `ContextHostParams.dispose`. `initializeTimeout` → `setupTimeout`. Flow-host drops `TERMINAL_STATES`; use `isTerminalRunState` from flow-client.

- Align with the current stack line: `@enkaku/*` 0.22.2, `@kokuin/token` 0.6.2, `@hozon/db` 0.5 (registering a different store definition under a taken name now throws `StoreAlreadyRegisteredError`), `@tejika/*`, `@sozai/*` and `@teikyo/oauth` on their OpenTelemetry v3 releases. Consumers sharing `@enkaku` and `@kokuin` types must upgrade in step. No mokei API changes.

### Patch Changes

- Updated dependencies:
  - @mokei/context-client@0.15.0
  - @mokei/context-protocol@0.15.0
  - @mokei/logger@0.15.0
