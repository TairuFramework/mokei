# MCP `2026-07-28` stateless core — complete

**Date:** 2026-08-02
**Branch:** `feat/mcp-2026-07-28-core`
**Status:** complete
**Scope:** B1, B2, B3, B5 and B6 from `docs/agents/plans/backlog/2026-06-20-mcp-draft-remaining.md`
**Milestone:** `docs/agents/plans/completed/2026-08-28-mcp-2026-07-28-migration-milestone.complete.md`

## Goal

Add MCP `2026-07-28` as a second protocol revision alongside `2025-11-25`, selected per client
and per server. `2026-07-28` removes the `initialize` handshake, protocol-level sessions and
`ping`, and carries the protocol version, client capabilities and client identity in each
request's `_meta` instead. mokei is a library, so it keeps speaking `2025-11-25` and gains the
new revision beside it.

Shipped in two plans against one branch: protocol + stdio first, then HTTP + host/CLI.

## What was built

**`context-protocol`** — a `versions/` directory with one file per revision, each exporting a
`PROTOCOL` record; a `PROTOCOLS` registry and `ProtocolVersion` union; the `2026-07-28` request
`_meta` envelope, `resultType`, and the `server/discover` request/result schemas; error codes
`-32020` `HEADER_MISMATCH`, `-32021` `MISSING_REQUIRED_CLIENT_CAPABILITY`, `-32022`
`UNSUPPORTED_PROTOCOL_VERSION`. Message-union validators became per-revision.

**`context-rpc`** — one subtraction: the hardcoded `ping` auto-answer. Ping dispatch moved up to
the client and server, driven by the resolved revision's method table. The package stays
MCP-version-agnostic, which is its charter.

**`context-client`** — `protocolVersion` required (`ProtocolVersion | 'auto'`); the handshake
generalized to a readiness promise; `discover()` added; capability gating backed by a lazily
fetched, `ttlMs`-honouring `server/discover` cache; construction refused when interactive
handlers meet a revision that can only carry them through MRTR; a typed error for
`resultType: 'input_required'`.

**`context-server`** — `protocolVersions` required; per-request revision resolution; the
`server/discover` handler; request-scoped log level replacing the connection-wide level;
mandatory caching hints on all six cacheable operations with a conservative
`{ ttlMs: 0, cacheScope: 'private' }` fallback; `resources.subscribe` never advertised for
`2026-07-28`.

**`http-client` / `http-server`** — a stateless POST path with no session creation, validation
or `Mcp-Session-Id`; `400`/`405` rules; no GET SSE endpoint for the stateless revision; the
`MCP-Protocol-Version` header derived from the outgoing request rather than connection state;
JSON-RPC errors carried by non-OK HTTP responses surfaced to their caller; a cap on concurrent
stateless exchanges.

**`host` / `session` / `cli`** — `protocolVersion` threaded through `addLocalContext`,
`addHTTPContext`, `createContext` and `Session.addContext`; `--protocol` on `mokei inspect` and
`/context add`; mokei's own bundled servers and fixtures serve both revisions.

## Key design decisions

1. **No "era" vocabulary.** Revisions are named by their date: `2025-11-25`, `2026-07-28`.

2. **Version files are siblings, not a chain.** Version-varying code lives in
   `versions/<revision>.ts`; both files compose the version-invariant modules (`rpc`, `tool`,
   `prompt`, `resource`, `client`, `server`) into their own envelope. Neither imports the other.

   The design originally called for the newest file to own shared implementations with older
   files importing from it. What shipped is stronger: under the original rule only the *older*
   file could be deleted safely, because deleting the newest would strand the older one's
   imports. As siblings, either can be deleted without touching the other, and a future revision
   adds a third sibling rather than relocating shared code into it. Deletion is the operation
   that recurs, so it is the one optimized for.

   Deletion cost is not symmetric: removing `versions/2025-11-25.ts` is one registry line;
   removing `versions/2026-07-28.ts` is that line plus `context-protocol`'s `procedure.ts`,
   which type-imports `DiscoverRequest` / `DiscoverResult` and feeds the `server/discover`
   entry. Type-only and trivial, but it is a second file.

3. **The revision is explicit at the core API, with two deliberate departures.**
   `ContextClient` and `ContextServer` require it, no default.
   - `ContextHost.add*Context` keeps it **optional, defaulting to `2026-07-28`** — the
     `createHostedContext` / `spawnHostedContext` pair had already shipped with an optional
     parameter, so requiring it on the siblings would be internally inconsistent and would churn
     every call site. The default is a real behaviour change for existing host callers, which is
     why mokei's own servers and fixtures were made to serve both revisions *before* the flip.
   - **The CLI defaults to `'auto'`, not `2026-07-28`** — it points at arbitrary third-party
     servers, nearly all of which speak only `2025-11-25`, so pinning the newest revision would
     make `mokei inspect <any existing server>` fail with `-32022`. `'auto'` costs one extra
     round trip against a server that answers `server/discover` with `-32601` immediately.
     Applies to both CLI entry points that take a revision.

4. **A protocol record at fixed seams**, not inline conditionals and not parallel class
   hierarchies. One record per revision supplies `decorateRequest`, `decorateNotification`,
   `readRequestMeta`, `wrapResult`, the client/server method tables, and the capability booleans
   `requiresHandshake`, `requiresRequestMeta`, `requiresCacheHints`,
   `requiresPerRequestLogLevel`. Consumers delegate. MRTR and `subscriptions/listen` plug into
   the same hooks later.

5. **Never branch on a version literal — branch on a capability boolean.** Behaviour derives
   from the record's booleans, never from comparing a version string. This was violated and
   caught three separate times during implementation, twice by reviewers and once by the fix for
   an earlier violation; it is the single most load-bearing convention in this area.

6. **Setup must be bounded on a revision with no handshake.** `setupTimeout` (30s, formerly
   `initializeTimeout`, old name kept as a deprecated alias) covers the `2025-11-25` handshake,
   the `'auto'` probe, *and* one `server/discover` issued at setup on any revision with
   `requiresHandshake: false`. Without that third case a pinned stateless connection has nothing
   bounded at all — `ContextRPC.request` arms a timer only when the caller passes a timeout — so
   a server that is spawned but never writes a byte hangs its host forever, where the same
   server fails in 30s on `2025-11-25`.

   An error *response* to that call is accepted as proof of life: a peer that does not implement
   discovery is still usable, so only silence fails setup. The call also seeds the capability
   snapshot the first gated call would otherwise fetch.

   It is not free. A client whose first call is capability-gated pays nothing, and an `'auto'`
   client is a request better off since the probe's result is no longer discarded — but a client
   whose calls are all ungated (`prompts/list`, `resources/read`, `getPrompt`) now sends one
   request per connection it did not send before. That is the price of the bound.

7. **Client-side interactive features refuse at construction.** Sampling, elicitation and roots
   exist in `2026-07-28` only through MRTR, which is not implemented. A `ContextClient` built
   with `createMessage`, `elicit` or `listRoots` handlers *and* that revision throws immediately
   rather than failing at first use.

8. **`error.data` carries no schema.** JSON-RPC 2.0 places no constraint on it, and mokei's
   stricter schema meant a peer sending a non-conforming `data` failed validation, had its frame
   dropped, and stranded its caller forever. `RPCError.data` is correspondingly `unknown` — a
   breaking type change in `@mokei/context-rpc`, taken because casting at the call site would
   have been a lie about what a peer can send.

## Verification

834 package tests, 0 failures. Integration suites 37 passed / 22 backend-gated skips / 0
failures.

Coverage: per-revision conformance fixtures (envelope required-field rejection, `resultType`
present and absent-means-complete, discover result shape, each new error code's `data`);
per-package unit tests (record hooks, request-scoped log level, session-header absence, method
table gating, mandatory caching hints including the unconfigured fallback); version-detection
cases over both transports; and a live SDK `2.0.0` interop suite.

**On the SDK peer.** Plan 1 concluded that SDK `2.0.0` does not implement `2026-07-28` and wrote
that into both plans and the stdio interop suite. That was false, and correcting it mattered:
`LATEST_PROTOCOL_VERSION = "2025-11-25"` names only what the *handshake* negotiates, and
`2026-07-28` has no handshake. The SDK ships `FIRST_MODERN_PROTOCOL_VERSION = "2026-07-28"`,
`SUPPORTED_MODERN_PROTOCOL_VERSIONS`, `isModernProtocolVersion()`, a wire codec,
`validateEnvelopeMeta()` and a `server/discover` handler. Servers come from `createMcpHandler`
(HTTP) and `serveStdio` (stdio, which accepts `{ legacy: 'reject' }` to serve the stateless
revision and nothing else); clients pin via
`new Client(info, { versionNegotiation: { mode: { pin: '2026-07-28' } } })`.

All four quadrants were driven against mokei with zero mokei changes. One shipped as a suite —
mokei client ↔ SDK server over HTTP. The other three are reachable through documented public
options and were simply not built; they are filed in the backlog.

Adding the real peer paid for itself the same day: it exposed that `Mcp-Name` was omitted for
`resources/read`, invisible to mokei-against-mokei tests because mokei's server validates no
request headers.

## Notable defects found and fixed during review

- **`Mcp-Name` written raw to a `Headers` object** — any non-Latin-1 URI threw a `ByteString`
  `TypeError`, making `resources/read` impossible for such resources on both revisions. Now
  base64-sentinel encoded through the existing `x-mcp-header` encoder, verified against a live
  SDK peer that decodes the sentinel before cross-checking it against the request body.
- **An over-strict `error.data` schema stranded callers** (decision 8 above).
- **The default flip removed the only unconditional setup timeout** (decision 6 above).

Each of the three was a consequence of a decision rather than a local mistake, which is why
eleven task-scoped reviews did not surface them and three whole-branch reviews did.

## Out of scope

MRTR (B7), `subscriptions/listen` (B4), the tasks extension, the authorization SEPs, and
`-32020` retry. Client-side caching of list results: mokei emits the required hints and honours
`ttlMs` only for its own `server/discover` cache, leaving result caching to consumers.

`-32020` and `-32021` have constants but no reachable emitter — `-32020`'s belongs to
`x-mcp-header` retry, and on `2026-07-28` a server sends no requests at all, so no handler can
need an undeclared client capability. Both revisit with MRTR.

section 3.
