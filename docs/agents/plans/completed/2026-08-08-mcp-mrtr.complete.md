## Goal

`2026-07-28` removes server-initiated top-level requests, so `sampling/createMessage`,
`elicitation/create` and `roots/list` had no wire mechanism there — the client and server both
refused all three at setup with `MRTRNotSupportedError`, leaving `2026-07-28` short of
`2025-11-25`'s capabilities. SEP-2322 ("MRTR") replaces them with `inputRequests` /
`inputResponses`. This branch implemented both sides and proved interop against
`@modelcontextprotocol/*` 2.0.0.

## What MRTR actually is (corrected from the milestone's original model)

The design record going into this branch (the milestone's "U1 problem" analysis and the `next/`
plan) modeled MRTR as an interleaved-frame **stream**: `tools/call` becoming
`1-request → (progress* · inputRequest* · result)`, with `inputResponse` frames forming a
*second* client→server correlation keyed by a continuation token, held open by
`_registerStreamExchange` / `ContinuationStore` in `@mokei/context-rpc`. That model was wrong.

MRTR is a **request-level retry loop**: `tools/call`, `prompts/get` and `resources/read` answer
**terminally** with `resultType: 'input_required'`, carrying embedded `inputRequests` and/or an
opaque `requestState`. The client fulfils the embedded requests locally and sends a **fresh**
request carrying `params.inputResponses` plus the echoed `requestState`; this repeats until
`resultType: 'complete'`. There is no stream, no continuation token, and no server-side
continuation state held open across rounds — a reconnect mid-flow costs exactly the in-flight
round, and cancellation is per-leg. `_registerStreamExchange` / `StreamHandlers` / `StreamFrame` /
`ContinuationStore` remain in `@mokei/context-rpc`, unused by MRTR; B4
(`subscriptions/listen`) is the only remaining candidate consumer of that seam.

## What was built, in order (tasks 1–10)

1. **Wire schema** (`context-protocol`) — embedded `InputRequest` / `InputResponse` schemas for
   the three MRTR-capable methods; `resultType` tightened from an `enum` admitting both terminal
   labels on every result to a `const: 'complete'` on ordinary results, with a distinct
   `inputRequiredResult` schema (`resultType: 'input_required'`, `inputRequests`, `requestState`)
   modeled as its own branch rather than a loosened `callToolResult`. Retry params
   (`inputResponses`, `requestState`) added to the three methods' request schemas;
   `inputRequestMethods` (`sampling/createMessage`, `elicitation/create`, `roots/list`) added to
   the `2026-07-28` `ProtocolDefinition` alongside the existing (empty) `serverMethods`.
2. **Client stops refusing** — `ContextClient`'s `#refuseUnsupportedHandlers` gates on
   reachability through *either* `serverMethods` or the new `inputRequestMethods`, so
   `createMessage` / `elicit` / `listRoots` handlers are accepted on `2026-07-28`.
3. **The driver** (`packages/context-client/src/mrtr.ts`, new) — `runInputRequiredFlow`: a pure,
   fully-injected loop (dispatch/retry/sleep/now all passed in) that fulfils a suspension's
   embedded requests, retries with `inputResponses` + echoed `requestState`, paces a
   `requestState`-only leg (`REQUEST_STATE_ONLY_PACING_MS`), and caps rounds
   (`DEFAULT_MAX_ROUNDS = 10`, matching SDK v2's own default) and total wall time
   (`maxTotalTimeout`).
4. **Wired into `ContextClient.request()`** — a suspended result triggers the driver by default
   (`inputRequired.autoFulfill`, default `true`), dispatching to the caller's own
   `createMessage`/`elicit`/`listRoots` handlers, so `callTool`/`getPrompt`/`readResource` return
   the same result type on both revisions. `allowInputRequired` opts a caller out to drive rounds
   itself; `RequestOptions` gained `allowInputRequired` / `maxTotalTimeout`, stripped by
   `splitRequestOptions` before reaching the wire.
5. **Server lifts the retry params** (`packages/context-server/src/mrtr.ts`, new) —
   `liftRetryParams` splits `inputResponses`/`requestState` off incoming params so a handler sees
   the same shape it would on `2025-11-25`; `resolveRequestState` runs an optional
   `RequestStateHooks.verify` over a returning `requestState` (SEP-2322 requires protecting its
   integrity when a server lets it influence authorization; unconfigured, the raw string reaches
   the handler untrusted).
6. **Return-based suspension** — a `2026-07-28` tool/prompt/resource handler suspends by
   *returning* `inputRequired({ inputRequests, requestState })` instead of awaiting an inbound
   request, and is **re-invoked** — a fresh call, not a resumed one — with
   `HandlerRequest.inputResponses` populated and `HandlerRequest.requestState` echoed back.
   `HandlerRequest` gained `inputResponses`, `requestState` and `mintRequestState`. Includes the
   post-review fix letting structured-output tool handlers suspend too (their return type had
   excluded `InputRequiredResult`).
7. **`-32021 MISSING_REQUIRED_CLIENT_CAPABILITY`** — `missingInputCapabilities` checks each
   embedded request's method against `INPUT_REQUEST_CAPABILITIES` and the request's own declared
   `ClientCapabilities`; an undeclared capability throws `MissingRequiredClientCapabilityError`
   before the round trip is wasted. Previously unreachable (`serverMethods` was empty on
   `2026-07-28`, so no handler could need an undeclared capability); now reachable and covered,
   including the requestState-only-suspension case.
8. **Interop** (`integration-tests`) — all four client × server × transport combinations (mokei
   client ↔ SDK server, SDK client ↔ mokei server, each over stdio and Streamable HTTP) pass on
   `2026-07-28`, proving both mokei's server-side suspension and its client-side auto-fulfilment
   against a real, independent peer.

## Design decisions

**Every MRTR round is an ordinary request/response pair.** No new correlation primitive, no
change to `ContextRPC`'s `#sentRequests` handling, no touch to `_registerStreamExchange`. The
retry loop lives entirely in `context-client/src/mrtr.ts` and `context-server/src/mrtr.ts`,
injected with the effects (dispatch, retry, sleep, clock) it needs so it is unit-testable without
a transport.

**`requestState` is opaque to the client and owned by the server.** The client only ever stores
and echoes back whatever string the server minted; it never inspects or interprets it. The server
may configure `mint`/`verify` hooks to protect its integrity, since SEP-2322 requires that when a
server lets it influence authorization or business logic — mokei ships no crypto or key management
of its own.

**The client-side handler surface stayed stable across revisions; the server-side one could
not.** `createMessage` / `elicit` / `listRoots` keep their `ClientParams` signatures on both
revisions — only the *wiring* differs, and the auto-fulfilment driver hides that from ordinary
callers. A `2026-07-28` handler body is shaped differently than its `2025-11-25` counterpart:
awaiting an inbound request becomes returning a suspension and being re-invoked.

**Auto-fulfilment is the default, not a corner case.** `inputRequired.autoFulfill` defaults to
`true` specifically so that `callTool`/`getPrompt`/`readResource` return the same result type
regardless of revision — a caller written against `2025-11-25` needs no code change to get the
same behavior on `2026-07-28`, unless it explicitly opts into driving rounds itself via
`allowInputRequired`.

call to make, not a foregone conclusion carried over from this branch.

## Follow-on

Raised during task 10's review and folded into this task rather than deferred further:
`packages/http-client/src/transport.ts`'s `createHTTPClient` forwards only `protocolVersion` to
the underlying `ContextClient` — `listRoots`/`elicit`/`createMessage` (and other `ClientParams`
fields) passed alongside it are silently dropped, since only `protocolVersion` is destructured out
and the rest goes to `HTTPTransport`, which does not declare those fields. A caller wanting MRTR
auto-fulfilment through the one-call HTTP helper needs to construct `HTTPTransport` and
`ContextClient` separately instead. `docs/guides/client.md` was corrected to say so; the ~3-line
code fix itself is not part of this branch's scope and is not yet tracked as backlog — worth
filing separately.
