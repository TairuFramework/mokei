# MCP `2026-07-28` defect wave — complete

**Date:** 2026-08-03
**Branch:** `fix/mcp-2026-07-28-defect-wave`
**Status:** complete
**Scope:** 3.1.1–3.1.5, 3.5.1 and 3.5.5 from `docs/agents/plans/backlog/2026-06-20-mcp-draft-remaining.md`
**Milestone:** `docs/agents/plans/milestones/2026-06-08-mcp-draft-migration.md`

## Goal

Close seven verified correctness defects in the MCP core across `context-rpc`,
`context-protocol`, `context-client` and `http-client`. Six were filed as follow-ons to the
`2026-07-28` stateless core work; 3.1.1 predates it and was merely measured by it.

Two of the seven change behavior a peer can observe rather than only fixing an internal fault: a
mokei server now answers requests concurrently where it used to serialize them, and a result that
used to validate may now be rejected.

## What was built

**`context-rpc`** — a new `RequestScheduler` unit owning bounded concurrency: a cap on running
requests, a FIFO queue behind it, and a busy response past the queue bound. The read loop stopped
awaiting handlers, so requests dispatch concurrently while notifications and responses keep wire
order. Any transport close — explicit dispose or peer EOF — now aborts every in-flight handler
signal. A frame that fails validation but carries a request id and no method is routed to its
exchange as a failure instead of being dropped, so its caller rejects rather than hanging forever.
An `onError` hook surfaces frames that can be neither validated nor routed. An opt-in
`defaultRequestTimeout` backstops a response that never arrives.

**`context-protocol`** — the result unions were vacuous on **both** revisions: `anyOf` containing
an open object with no `required` keys admits any object at all, so the remaining branches never
got a say. A closed `emptyResult` branch replaced the bare open base, and `2026-07-28` gained a
revision-local `serverResult`/`serverResponse`/`serverMessage` that enforces the `resultType`
discriminator, with `discoverResult` as a union member and a purpose-built `inputRequiredResult`
for SEP-2322-shaped suspended results.

**`context-client`** — a `requestTimeout` param; a supported-version guard that throws
`UnsupportedProtocolVersionError` at construction for an unknown `protocolVersion` pin, where the
bad string previously fell through to auto-probing; the `as DiscoverResult` cast replaced by real
validation.

**`http-client`** — a per-request-ID `AbortController` that now survives past the response headers,
aborted when an outgoing `notifications/cancelled` names that ID on `requiresHandshake: false`
revisions, and on `dispose()`. Previously an aborted `callTool` rejected locally while the server
ran the tool to completion.

**`context-server` / `context-client` params** — the scheduler bounds and the `onError` hook are
surfaced through both, so the limits are not hardcoded per server and the hook is reachable.

**`host`** — a pinned version is validated *before* the child server process is spawned.

## Key design decisions

**Cap and queue, never stop reading.** Back-pressure could have been applied by pausing the read
loop under load. It is not: the loop always reads, because `notifications/cancelled` must stay
deliverable exactly when a server is saturated. A request past the queue bound gets an error
response instead.

**`INTERNAL_ERROR` (-32603) for the busy response.** A dedicated code in the server-error range
would read better to a client deciding whether to retry, but mokei's existing custom codes
(-32020..-32022) all come from SEPs, so inventing -32023 risks colliding with a future one.

**An unset request timeout means unbounded.** No request gained a bound it did not have. A blanket
default would kill a long `tools/call`; the real fix for a hang is the drop-path rejection, not a
timer. Setup keeps its own independent timeout.

**The open `result` base stayed open.** It is the `allOf` base of every concrete result schema and
must admit extension. The defect was that the bare base was also a *member* of the union — fixed by
adding a closed sibling branch, not by tightening the base.

**Abort on any close, with no new close-reason distinction.** Dispose and peer EOF both already
funnel through one path, so one line covers both.

**Cancellation stays on the notification channel for session revisions.** Dropping the POST is
only correct on the stateless path; a session server cannot read a dropped POST as a cancellation,
and dropping it would kill the stream carrying the response.

## Status

All eleven planned tasks landed, each behind its own review gate, plus a final whole-branch review
and a fix round answering it. 24 commits. `pnpm build` clean, 887 package tests passing, biome
clean; integration suites green (count varies with which local model backends are reachable — the
suites probe for them at collection time).

The final review caught three defects that the per-task reviews structurally could not see, all
fixed before merge:

- a peer reusing a request ID bypassed the concurrency cap entirely and left most handlers
  unreachable by the close-abort, because both scheduler maps are keyed by the peer's ID;
- the new version-pin guard turned a degraded probe into a **leaked child process**, since `host`
  spawned the server before constructing the client that now throws;
- the sole test guarding "`onError` does not fire on ordinary aborts" could not fail, because it
  only aborted an outbound request and never drove the inbound handler it defined.

Tightening result validation also exposed three test fixtures that had never matched what a real
server sends — a `roots` entry keyed `url` instead of `uri`, a `prompts` `arguments` object where
the schema requires an array, and image `data` that was not valid base64. All three were fixture
bugs, not tests weakened to pass.

## Public API changes

No changelog or changeset mechanism exists in this repo; recording these is the release process's
job. The observable changes are: `ContextClient`'s constructor now **throws** for an unknown
`protocolVersion` pin where it used to silently auto-probe; `UnsupportedProtocolVersionError`'s
`expected` param went required → optional with a new message form; new `ClientParams.requestTimeout`
and `RPCParams.{defaultRequestTimeout,maxConcurrentRequests,maxQueuedRequests,onError}`; new
exports `emptyResult`/`EmptyResult`, `discoverResult` and `RequestScheduler`; a new
`INTERNAL_ERROR` "Server busy" wire error; and inbound result validation that now rejects frames
it previously accepted on **both** revisions.

failure mode is a false red on a stalled CI box, never a false green.
