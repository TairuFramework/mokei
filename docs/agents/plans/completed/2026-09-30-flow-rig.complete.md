# Flow rig, phase 1 (local rig) -- complete

**Status:** complete
**Date:** 2026-09-30
**Branch:** `feat/flow-rig`
**Milestone:** [flow rig](../milestones/2026-09-30-flow-rig-milestone.md), phase 1

## Goal

Run decision flows that use System One, sibling MCP servers and desktop input locally, driven from Claude Code
through MCP. Phase 1 of the flow rig milestone; phases 2 (integration/e2e harness) and 3 (session, host and CLI
features) build on it.

## Key design decisions

- **Plain Node script, not a package.** Everything lives in `scripts/flow-rig/` and imports the built `lib/` of
  workspace packages by relative path. No package code changed.
- **Facade MCP server.** Claude Code cannot call the decision-flow tools directly: they run only as MCP tasks, and
  each run needs a single-use `dev.mokei/flow-grant` minted by `DecisionFlowWiring.wrapApproval` and bound to the
  tool name and an args digest. The rig approves a run itself, calls the flow tool with `task: 'handle'` using the
  identical args object, and exposes `start_flow` / `flow_status` / `cancel_flow` plus `list_flows` and
  `check_flow` pass-throughs.
- **Input goes to the desktop, not upstream.** The rig never calls `tasks.wait` (which answers input requests
  itself). It polls `tasks.get`, hands each input request to the `@mokei/host-desktop` elicit handler with the run
  id as the inbox key, and answers with `tasks.update`. Inbox mode is the default (`prompt_input`,
  `answer_input`, `decline_input` tools); blocking dialogs are opt-in.
- **Input record state machine.** One record per request key: `asking`, `sending` (holds the result until
  `tasks.update` succeeds, retried up to 3 attempts), `done`. A key that leaves the snapshot withdraws its prompt
  (aborted with `TaskInputWithdrawnError`); a late handler result is dropped; a `-32602` update means the key is
  no longer pending.
- **Poll failure is not task failure.** Three failed polls give state `unknown` with backoff up to 5 s; a later
  success restores the real state.
- **Approval by allowlist.** A run whose static tool plan fits the configured tool-id globs (`*` stays within one
  segment) is approved; otherwise a desktop confirm dialog decides (`confirm: deny|approve` for scripted runs).
  A caller that cancels `start_flow` during approval never starts the run.
- **Real or fake predictor.** `system-one:predict` by default; a scripted fake (`fakeAnswers`) for runs without
  System One. The fake is a plain `Predictor`, so flow plans exclude `system-one:predict`.
- **Bounded shutdown.** Stop watchers, abort approvals and open prompts, then within 5 s wait for in-flight
  starts (cancelling any task they create) and updates and cancel live runs, then dispose inbox, handlers, flow
  wiring and session.

## What was built

- `scripts/flow-rig/`: `config.mjs`, `fake-predictor.mjs`, `inputs.mjs`, `runs.mjs`, `approval.mjs`,
  `serve.mjs`, `smoke.mjs`, `rig.config.json`, sample flows `demo/triage`, `demo/ask`, `demo/nested`, and a
  README with the config reference, tools table and manual QA checklist.
- 43 `node:test` unit tests (`pnpm run test:flow-rig`) and an 8-check end-to-end smoke run over stdio
  (`pnpm run smoke:flow-rig`).
- Root `.mcp.json` registers the rig for Claude Code; root `lint` now covers `./scripts`.
- Milestone findings recorded for phase 3.
- Manual macOS QA checklist passed on 2026-10-01 against a local `laya-serve` System One. It found that the
  system-one sibling needs `SYSTEM_ONE_MODEL`, now set in `rig.config.json`.

## Open

- Known edge left for phase 3: a caller that cancels `start_flow` while the flow tool call itself is in flight
  still registers a run whose id never reaches Claude Code (a `list_runs` tool would cover it).
