# Flow CLI and MCP

**Status:** complete
**Date:** 2026-10-03
**Milestone:** [flow daemon](../milestones/2026-10-01-flow-daemon-milestone.md), sub-project 4
**Branch:** `feat/flow-cli`

## Outcome

The `mokei` CLI drives the flow daemon through `daemon`, `flows`, `runs` and `inbox` commands, and
`mokei flows mcp` exposes the same control to agents over stdio MCP. The flow rig and its suite are deleted;
the repository `.mcp.json` now runs `mokei flows mcp`.
A new portable package, `@mokei/flow-client`, holds the `FlowControl` interface, the daemon adapter, wait helpers
and the MCP server. `@mokei/flow-host` adds `createLocalFlowControl` for in-process use.
The published declaration dependency fixes are folded in and guarded by the `pnpm test:packed` packed-consumer check in CI.

## Key decisions

- Agents cannot approve runs. Over MCP, approval items are only routed to a human through `prompt_input`
  (desktop dialog). Runs matching the `flows.json` approval globs still start at once.
- Plain MCP tools, not MCP tasks: Claude Code does not support tasks, and task elicitation would bypass the inbox.
- The MCP server targets `FlowControl`, so it works against the daemon or an in-process `FlowHost`.
- `@mokei/flow-client` is a new package because the CLI, `flows mcp` and the monitor (sub-project 5) all consume it.
- CLI output is human-readable by default with `--json` on every command, one JSON document per command.
- `runs start` returns at once; `--wait` follows the run to a terminal state and answers inputs and approvals in the
  terminal. Declining an approval there (n or Esc) leaves the item pending; `inbox decline` denies the run.
  Ctrl-C in a terminal prompt aborts the command.
- `wait_flow` and `waitForRun` return the latest status with `timedOut: true` on timeout, doing one final read when
  none succeeded; they reject only with a real error.
- `daemon stop` passes the expected socket to `@tejika/process` (0.5.2) so it never signals a daemon serving another
  socket, and reports a forced kill. `restart` starts after a stop or when nothing was running.
- On macOS, desktop notifications use `alerter` when installed (falling back to `osascript`, whose notifications open
  Script Editor on click). Clicking a single-item notification opens that item's desktop prompt; each notification
  is removed when its item settles.
- Terminal prompts reuse `@tejika/cli`, `@tejika/ui` and `@inkjs/ui` primitives; optional boolean and select fields
  cannot be skipped.
- The packed-consumer check patches three third-party manifest gaps with `packageExtensions` (requested upstream).

## Verification and review

All implementation tasks passed task reviews. The whole-branch review found one Important issue (a short `wait_flow`
timeout reported a false `DISCONNECTED`) and eight Minor ones; all were fixed and passed a scoped re-review.
Build, lint, typechecks, the full test suite, `pnpm test:packed` and the flow end-to-end suites passed.

Manual macOS QA passed on 2026-10-03 through the CLI and Claude Code over MCP, using an isolated daemon with desktop
notifications on. It covered notification policy, desktop prompts (accept, decline, cancel, settled elsewhere,
caller disconnect, unsupported schema), terminal `--wait` including Ctrl-C, restart recovery, daemon commands,
and MCP `start_flow`, `wait_flow` and `prompt_input`. This also completes the native desktop QA deferred from
sub-project 3.

Follow-ons are in the [flow client follow-ons](../backlog/2026-10-03-flow-client-follow-ons.md) backlog. Sub-project 5
should revisit notification clicks so they open the monitor inbox screen when the monitor is running.
