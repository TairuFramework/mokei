# Flow Rig Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local Node script that runs decision flows with System One, MCP siblings and desktop input, driven from Claude Code through a facade MCP server.

**Architecture:** `scripts/flow-rig/serve.mjs` owns a `NodeSession` with stdio siblings, registers flows with `addDecisionFlow`, and serves a small stdio `ContextServer` to Claude Code. Pure logic (config, allowlist, fake predictor, approval, input reconciliation, run watching) lives in small sibling modules with `node:test` unit tests; `serve.mjs` wires them and `smoke.mjs` checks the whole rig end to end.

**Tech Stack:** Node ESM (`.mjs`), `node:test` + `node:assert/strict`, built `lib/` of `@mokei/session-node`, `@mokei/decision-flow-server`, `@mokei/host-desktop`, `@mokei/context-server-node`, `@mokei/host-node`.

**Spec:** `docs/superpowers/specs/2026-09-30-flow-rig-design.md`. Milestone: `docs/agents/plans/milestones/2026-09-30-flow-rig-milestone.md` (phase 1).

## Global Constraints

- Plain script under `scripts/flow-rig/`; no new package, no changes to anything under `packages/` or `mcp-servers/`.
- Import workspace packages by relative path to their built entry, e.g. `../../packages/session-node/lib/index.js` (the repo root has no `@mokei/*` dependencies). `pnpm build` must have run.
- Kebab-case file names. `pnpm` only, never `npm`/`npx`. Run repo scripts as `rtk proxy pnpm run <script>`.
- All rig logs go to stderr; stdout carries MCP.
- Time values are injectable (`pollMs`, `sleep`, `now`) so unit tests never wait on real timers longer than a few ms.
- Committed docs never contain local absolute paths.

## Review Focus

1. **Answer racing withdrawal.** A handler resolving after its key left `inputRequests` must never call `tasks.update` (Task 3).
2. **Retry of a failed `tasks.update`.** The stored result is resent while the key is still pending, never re-asked on the desktop, and gives up after three attempts (Task 3).
3. **Grant digest mismatch.** The object passed to approval (stringified) and the `arguments` passed to `callTool` must be the same object; a copy that reorders or adds `input: undefined` breaks the grant (Task 5).
4. **Shutdown during `start_flow`.** A start already past approval that creates a task after shutdown began must be cancelled (Task 4).
5. **Poll failure is not task failure.** Three failed polls give `unknown`, later success restores the real state (Task 4).

### Task 3: Input tracker (per-run reconciliation)

**Files:**
- Create: `scripts/flow-rig/inputs.mjs`
- Create: `scripts/flow-rig/test/inputs.test.mjs`

**Interfaces:**
- Produces: `createInputTracker({ ask, update, log, maxAttempts = 3 })` where
  - `ask(requestKey: string, request: InputRequest, signal: AbortSignal): Promise<ElicitResult>`
  - `update(responses: Record<string, ElicitResult>): Promise<void>`
  - returns `{ reconcile(snapshot: DetailedTask): void, abortAll(): void, settled(): Promise<void>, error: string | undefined, records: Map<string, { state: 'asking'|'sending'|'done' }> }`.
  - `settled()` resolves when no `tasks.update` is in flight.
- Stale update error: `error.code === -32602` (`INVALID_PARAMS` from `TaskManager.update` for a key no longer pending).

The state machine is exactly the spec's Inputs section (steps 1–5 of reconciliation, plus the handler-resolution and error bullets). Follow it literally.

- [ ] **Step 1: Write failing tests** (fake `ask` returning controllable deferreds, fake `update` recording calls):
  - New key in an `input_required` snapshot calls `ask` once; reconciling the same snapshot again does not call it again.
  - Key missing from a later snapshot while `asking`: its signal aborts, record `done`; resolving the deferred afterwards never calls `update`.
  - Snapshot with status `working` aborts every `asking` record.
  - Handler resolves `{ action: 'accept', content: { value: 'x' } }`: `update` called with `{ [key]: result }`, record `done` after it resolves.
  - Handler resolves `decline`: sent unchanged.
  - Handler rejects: `update` called with `{ [key]: { action: 'cancel' } }` and `log` called.
  - `update` rejects with `{ code: -32602 }`: record `done`, `log` called, no retry.
  - `update` rejects with another error: record stays `sending`; next reconcile with the key still present resends the stored result without calling `ask`; after 3 failed attempts record `done` and `tracker.error` mentions the key.
  - `sending` record whose key is missing from the snapshot (no update in flight): marked `done`.
  - `abortAll()` aborts every `asking` signal; a later resolution does not call `update`.
  - `settled()` waits for an in-flight `update`.
- [ ] **Step 2:** tests fail.
- [ ] **Step 3: Implement** `inputs.mjs`.
- [ ] **Step 4:** tests pass; lint clean.
- [ ] **Step 5: Commit** `feat(flow-rig): input request reconciliation`.

### Task 4: Run manager (start, watch, status, cancel, shutdown)

**Files:**
- Create: `scripts/flow-rig/runs.mjs`
- Create: `scripts/flow-rig/test/runs.test.mjs`

**Interfaces:**
- Consumes: `createInputTracker` (Task 3).
- Produces: `createRunManager({ client, approve, ask, listPending, log, pollMs = 500, maxBackoffMs = 5000, sleep })` where
  - `client`: `{ callTool(params), tasks: { get(id), update(id, responses), cancel(id) } }` (the flow context's `ContextClient`).
  - `approve({ runId, toolName, args, signal }): Promise<{ approved: true, meta } | { approved: false, reason }>` (Task 5 supplies it).
  - `ask(runId, requestKey, request, signal)`: the desktop handler adapter.
  - `listPending(runId): Array<{ id, message, requestedSchema }>`.
  - returns:
    - `start({ toolName, args }): Promise<CallToolResult>` — `structuredContent: { runId }` on success; error results `Flow denied: <reason>`, or the flow tool's own synchronous `CallToolResult` unchanged.
    - `status(runId): CallToolResult` — `structuredContent: { state, pending, result?, error? }`; unknown id gives an error result.
    - `cancel(runId): Promise<CallToolResult>` — `structuredContent: { state }`.
    - `shutdown({ timeoutMs = 5000 }): Promise<void>` — the spec's four shutdown steps.
- `runId` is `crypto.randomUUID()`.

- [ ] **Step 1: Write failing tests** with a fake client whose `tasks.get` returns queued snapshots and `sleep` resolves immediately:
  - `start` calls `approve` then `callTool({ name, arguments: args, _meta: meta, task: 'handle' })` with the identical `args` object (`assert.equal` on identity).
  - Denial returns an error result `Flow denied: nope` and never calls `callTool`.
  - `callTool` returning a `CallToolResult` (no `taskId`) is returned as is and no run is registered.
  - Watcher: `working`, `input_required` (with one key), `completed` snapshots → `status` goes `working` → `input_required` with `pending` from `listPending` → `completed` with `result`; `ask` was called for the key.
  - Three consecutive `tasks.get` rejections → `state: 'unknown'` with `error`; a following successful snapshot restores its state.
  - `cancel` calls `tasks.cancel(taskId)`; status of unknown runId is an error result.
  - Shutdown: in-progress `approve` receives an aborted signal; a `start` whose `callTool` resolves after shutdown began gets `tasks.cancel` for its task; `tasks.cancel` called for each live run; resolves within `timeoutMs` even when `tasks.cancel` never settles.
- [ ] **Step 2:** tests fail.
- [ ] **Step 3: Implement** `runs.mjs`. Backoff after failures: `min(pollMs * 2^(failures-2), maxBackoffMs)` once `failures >= 3`, else `pollMs`.
- [ ] **Step 4:** tests pass; lint clean.

**Interfaces:**
- Consumes: everything from Tasks 1–5.
- Produces: `main({ configPath, stdio = true }): Promise<{ tools, shutdown }>` exported for tests; running the file directly calls `main` with `process.env.FLOW_RIG_CONFIG ?? '<dir>/rig.config.json'` and `serveProcess`.

Wiring (spec Architecture section):
- Desktop: `createInputInbox()` + `inbox.registerAnswerSurface()` in inbox mode; `createDesktopElicitHandler({ mode: config.input, inbox })` for inputs; a second `createDesktopElicitHandler({ mode: 'dialog' })` for `confirmDialog`, asking a one-property boolean form (`approve`, title listing the flow name and its tools) and treating anything but `accept` with `approve: true` as `false`.
- Session: `new NodeSession({ elicit: (request) => inputs(request) })`, then `addContext` per sibling; skip `system-one` when `predictor === 'fake'`. A spawn failure logs and exits 1.
- Flows: read every `*.json` in `flowsDir`; `addDecisionFlow(session, { key: 'flow', flows, predictor: fake ? createFakePredictor(config.fakeAnswers) : undefined })`. A registration error logs the file names and message and exits 1.
- Run manager: `client = session.contextHost.getContext('flow').client`; `ask(runId, key, request, signal)` calls the inputs handler with `{ key: runId, params: request.params, signal }`; `listPending(runId)` filters `inbox.list()` by `entry.key === runId`.
- Facade tools (spec table): `list_flows` and `check_flow` call `flow:list_flows` / `flow:check_flow` through `session.contextHost.callNamespacedTool`. `start_flow` resolves the tool name with `flowToolName` (registered id) or `run_flow` (inline) and builds `args` once (`input ?? {}` for registered; `{ definition, input }` for inline, omitting `input` when undefined), exactly one of `flow`/`definition` else error result. `prompt_input`, `answer_input`, `decline_input` (inbox mode only) call `inbox.prompt(id, signal)`, `inbox.answer(id, value)`, `inbox.decline(id)`, mapping `InboxAnswerInvalidError` and unknown ids to error results.
- Shutdown on `SIGINT`, `SIGTERM`, stdin `end`: `runs.shutdown()`, then dispose inbox, both desktop handlers, flow wiring, session; then `process.exit(0)`.

Sample flows (definitions in the `@sozai/flow-graph` format used by `packages/decision-flow-server/test/driver-input.test.ts` and the `decide` node in `packages/decision-flow/README.md`):
- `demo/triage`: `decide` with one choice question `label` (options `bug`, `question`), routes to a `tool` node `sqlite:sqlite_get` with args `{ sql: 'SELECT :label AS label', parameters: { label: <ref to the decide answer> } }`, then `end` with the row as output.
- `demo/ask`: `input` node with a string `value`, `decline` edge to an `end` with outcome `declined`, success `end` with outcome `answered` and the value as output.
- `demo/nested`: `call` to `demo/ask` version 1, `end` passing through `outcome` and `output`.
