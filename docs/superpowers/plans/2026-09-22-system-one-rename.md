# System One Rename Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rename the unreleased Laya classification packages and public API to the generic "System One" name, keeping Laya only on `laya.cpp`-specific pieces.

**Architecture:** Pure rename, no behavior change. Directories move with `git mv`; identifiers change through one ordered `perl` substitution map, followed by a short list of hand edits for prose strings. Task 1 renames all code and workspace config (both packages together, so the workspace builds at every commit). Task 2 renames and rewrites the docs and runs the final verification.

**Tech Stack:** TypeScript (ESM, NodeNext), pnpm workspace, turbo, vitest, Biome, swc.

**Spec:** `docs/superpowers/specs/2026-09-22-system-one-rename-design.md`

## Global Constraints

- Naming only: wire contract, runtime behavior, schemas, and package version `0.13.1` do not change.
- No deprecation aliases and no compatibility re-exports; both packages are unreleased.
- Rename rule: the `Laya` prefix becomes `SystemOne`; `HTTPLaya` becomes `HTTPSystemOne`; `LAYA_` env vars become `SYSTEM_ONE_`.
- Laya survives only on `laya.cpp`-specific pieces: the `batch` option JSDoc, the `laya serve` / GGUF docs section, the backlog item for the in-process `laya-ggml-*` backend, model-family examples (`english`), and the `laya` package keyword.
- `@mokei/system-one-client` stays platform-neutral: no `node:*` imports.
- Lint with `rtk proxy pnpm run lint`, never `pnpm lint`. `pnpm` / `pnpx` only, never `npm` / `npx`.
- Commits end with:

## Review Focus

1. Error runtime names — every error class's `name` property must equal its new class name; the existing test covers only 3 of 6 classes, so Task 1 extends it to all six.
2. Stale build output — `@mokei/mcp-system-one` tests resolve `@mokei/system-one-client` through its built `lib/`, so the client must be rebuilt before the MCP tests run, or they pass against stale output or fail to resolve.
3. Lockfile drift — after the package renames, `pnpm install --frozen-lockfile` must report up to date; a stale `pnpm-lock.yaml` breaks CI installs.
4. Leftover Laya names — `git grep` must show no `Laya`-prefixed identifier, no `LAYA_` env var, and no `laya-client` / `mcp-laya` package or path anywhere outside the allowed survivors.
5. MCP launch config — `mcp-servers/config.json` must point at `mcp-servers/system-one/lib/serve.js` with `SYSTEM_ONE_URL`; a stale path silently breaks the dev MCP config.

- [ ] **Step 2: Apply the identifier substitution map**

Run from the repo root. The rule order matters: `HTTPLaya` and `createLaya` / `CreateLaya` have no word boundary before `Laya`, so they need their own rules before the generic one.

```bash
git ls-files packages/system-one-client mcp-servers/system-one \
  | grep -E '\.(ts|json)$' \
  | xargs perl -pi -e '
      s/HTTPLaya/HTTPSystemOne/g;
      s/\bcreateLaya/createSystemOne/g;
      s/\bCreateLaya/CreateSystemOne/g;
      s/\bLaya(?=[A-Z])/SystemOne/g;
      s{\@mokei/laya-client}{\@mokei/system-one-client}g;
      s/\bLAYA_/SYSTEM_ONE_/g;
    '
```

This covers every exported and internal identifier, the error classes' `this.name = '...'` strings, the MCP exports, the env vars, and the MCP package's dependency and import of the client package.
