# MCP `2026-07-28` stateless core — design

**Date:** 2026-07-29
**Branch:** `feat/mcp-2026-07-28-core`
**Scope:** B1, B2, B3, B5 and the `logLevel` half of B6 from
`docs/agents/plans/backlog/2026-06-20-mcp-draft-remaining.md`
**Milestone:** `docs/agents/plans/milestones/2026-06-08-mcp-draft-migration.md`

## Goal

Add MCP `2026-07-28` as a second protocol version alongside `2025-11-25`, selected
explicitly per client and per server. The spec released 2026-07-28 (SDK `2.0.0` stable
shipped with it), so every shape below is pinned against the final revision rather than the
draft.

`2026-07-28` removes the `initialize` handshake, protocol-level sessions, and `ping`, and
carries protocol version, client capabilities, and client identity in each request's
`_meta`. mokei is a library, so it keeps speaking `2025-11-25` and gains the new revision
beside it — the coexistence decision recorded in the milestone.

B6 comes along in full — the `logLevel` `_meta` key and the removal of `logging/setLevel`
and `notifications/roots/list_changed` are one bullet of SEP-2575, and splitting them costs
more than doing them together.

Out of scope, tracked in the backlog: MRTR (B7), `subscriptions/listen` (B4), the tasks
extension, the authorization SEPs, and `-32020` retry (G7 part 5). Client-side caching of
list results is also out of scope: mokei emits the required hints and honors `ttlMs` only
for its own `server/discover` cache, leaving result caching to consumers.

> **Amended (2026-08-01) — the error table's `-32020` and `-32021` still have no emitter.**
> `-32020` (`HEADER_MISMATCH`): the constant exists, the emitter belongs to `x-mcp-header`
> retry, which is backlog (G7 part 5). `-32021` (`MISSING_REQUIRED_CLIENT_CAPABILITY`): the
> constant exists and has **no reachable emitter** — on `2026-07-28` a server sends no requests
> at all (`PROTOCOL.serverMethods` is empty), so no handler can need an undeclared client
> capability, and `ServerClient.createMessage` / `elicit` / `listRoots` throw
> `MRTRNotSupportedError` first. Revisit with MRTR (B7). User decision; both are recorded in
> `docs/agents/plans/backlog/2026-06-20-mcp-draft-remaining.md`.

## Decisions

1. **No "era" vocabulary.** Versions are named by their revision: `2025-11-25`,
   `2026-07-28`. Code, types, and docs use `ProtocolVersion`.
2. **Newest version owns shared implementations.** Version-varying code lives in
   `versions/<revision>.ts`; the newest file holds anything two versions share, and older
   files import from it. Dropping a version is deleting its file plus one registry line, not
   moving code. The cost is the inverse case: introducing a future revision moves shared
   implementations into the new file. Deletion is the operation that recurs, so it is the
   one optimized for.

   > **Amended (2026-08-01), after the whole-branch review — this is not what shipped, and
   > what shipped is better.** `versions/2025-11-25.ts` does *not* import from
   > `versions/2026-07-28.ts`. Both are **siblings** over the version-invariant modules
   > (`../rpc.js`, `../tool.js`, `../prompt.js`, `../resource.js`, `../client.js`,
   > `../server.js`, …), each composing those shared bodies into its own envelope.
   >
   > This is strictly stronger than the decision as written. Under the decision, only the
   > *older* file could be deleted safely — deleting the newest would strand every import the
   > older one made of it. Under what shipped, **either** file can be deleted without touching
   > the other, and introducing a future revision adds a third sibling instead of relocating
   > shared implementations into it. The recurring operation the decision set out to optimize
   > is still optimized, and the inverse case it accepted as a cost no longer exists.
   >
   > The cost is not identical in both directions, though. Deleting `versions/2025-11-25.ts`
   > is one registry line in `versions/index.ts`. Deleting `versions/2026-07-28.ts` is that
   > line plus `packages/context-protocol/src/procedure.ts`, which type-imports
   > `DiscoverRequest` / `DiscoverResult` from it — one `import type` and the `server/discover`
   > entry it feeds. Type-only and trivial, but it is a second file, and the point of this
   > amendment is the precision of the deletion cost.
   >
   > The layout sketch below and the `2026-07-28.ts` / `2025-11-25.ts` paragraph following it
   > describe the decision as written, not as shipped; read them with this amendment.
3. **Version is explicit at the core API.** `ContextClient`, `ContextServer`, and
   `ContextHost.add*Context` require it — no default. Every layer that must supply a value
   (CLI config schema, examples, docs, test helpers) uses `2026-07-28`.

   > **Amended (2026-08-01) — two user decisions departed from this.**
   >
   > **(a) `ContextHost.add*Context` keeps `protocolVersion` optional, defaulting to
   > `'2026-07-28'`.** Plan 1 had already shipped `createHostedContext` / `spawnHostedContext`
   > with an optional parameter, so making the three `add*Context` siblings required would be
   > internally inconsistent and would churn every call site. The default is a real behavior
   > change for existing host callers, which is why mokei's own servers and fixtures were made
   > to serve both revisions *before* the default was flipped. `ContextClient` and
   > `ContextServer` do still require it.
   >
   > **(b) The CLI defaults to `'auto'`, not `'2026-07-28'`.** The CLI points at arbitrary
   > third-party servers, nearly all of which speak only `2025-11-25`; pinning the newest
   > revision would make `mokei inspect <any existing server>` fail with `-32022`. `'auto'`
   > costs one extra round trip against a server that answers `server/discover` with `-32601`
   > immediately. `--protocol` still pins explicitly.
   >
   > This applies to **both** CLI entry points that take a revision: `mokei inspect` and the
   > chat session's `/context add`. `/context add` briefly defaulted to `'2026-07-28'` instead,
   > but that was a gap rather than a decision — its local was left unassigned, so the host's
   > default leaked through — and it was corrected. The host-level `'2026-07-28'` default in
   > (a) is unchanged; this is a CLI-layer default, which is where the decision places it.
4. **Both transports.** stdio and Streamable HTTP both speak both versions, so B1 (session
   removal) lands in this slice.
5. **Client-side interactive features refuse at setup.** Sampling, elicitation, and roots
   exist in `2026-07-28` only through MRTR, which is B7. A `ContextClient` constructed with
   `createMessage`, `elicit`, or `listRoots` handlers *and* `2026-07-28` throws at
   construction.
6. **Approach: protocol record at fixed seams**, not inline conditionals and not parallel
   class hierarchies. One record per version supplies a small set of hooks; consumers
   delegate. B4 and B7 later plug into the same hooks.

## Delivery — two plans

This spec ships in two plans against the same branch.

**Plan 1 — protocol + stdio.** `context-protocol` (`versions/`, error codes, envelope and
discover schemas), `context-rpc` (ping removal), `context-client` and `context-server` in
full, and the stdio `'auto'` probe. Verification: conformance fixtures, per-package unit
tests, the stdio interop suite (schema-oracle rather than the two live SDK combinations this
line planned — see the amendment under Verification item 4), and the stdio version-detection
cases.

Because `protocolVersion` becomes required in plan 1, every existing call site in `host`,
`session`, `cli`, and the tests must pass `'2025-11-25'` explicitly as part of plan 1 — a
mechanical change that keeps the build and the regression gate green. Plan 1 adds no
configuration surface above the core.

**Plan 2 — HTTP + host/CLI.** `http-client` (protocol-version header, no session header, no
`Last-Event-ID`, `400`-body probe), `http-server` (stateless request path, `400` rules, no
GET endpoint for `2026-07-28`), `host` (`protocolVersion` on `addLocalContext`,
`addHTTPContext`, `createContext`, with per-config probe caching), `session` / `agent`
plumbing, and the CLI config field defaulting to `2026-07-28`. Verification: the two HTTP
interop combinations and the HTTP version-detection cases.

## Architecture

### Version-invariant vs version-varying

Only the **envelope** (request `_meta` requirements, result `resultType` and `serverInfo`)
and the **method table** differ between the two revisions. Every payload — `Tool`,
`Prompt`, `Resource`, content blocks, result bodies, capabilities, `Implementation`,
`Icon`, pagination, `CacheableResult` — is identical. Sharing is the default; duplication is
the exception.

### `context-protocol` layout

```
src/
  rpc.ts, tool.ts, prompt.ts, resource.ts, …   version-invariant, stay in place
  versions/
    2026-07-28.ts   newest — owns shared implementations
    2025-11-25.ts   imports from 2026-07-28, overrides what differs
    index.ts        PROTOCOLS registry + ProtocolVersion union
```

Files that never varied by version do not move into `versions/`.

`2026-07-28.ts` defines the per-method param and result *bodies* plus `wrapRequest` /
`wrapResult`. `2025-11-25.ts` imports those bodies and re-wraps them in its own envelope, so
the methods common to both revisions are written once. Methods unique to one revision
(`ping`, `initialize`, `logging/setLevel`, `server/discover`) are declared only in the file
that has them — the method tables differ without a conditional.

### The protocol record

Each version file exports one `PROTOCOL` record:

| Field | `2025-11-25` | `2026-07-28` |
|---|---|---|
| `decorateRequest` | trace `_meta` only | + `protocolVersion`, `clientCapabilities`, `clientInfo`, `logLevel` |
| `readRequestMeta` | `{}` | parse and require version + capabilities, else `-32602` |
| `wrapResult` | passthrough | + `resultType: 'complete'`, `_meta` `serverInfo` |
| `methods` | `ping`, `initialize`, `logging/setLevel`, … | `server/discover`, … |
| `open` | `initialize` → await → `notifications/initialized` | no-op |

Adding a future revision is one new file plus one registry line.

### Wire shapes (pinned against the final spec)

Request `_meta` keys, from
[basic/index](https://modelcontextprotocol.io/specification/2026-07-28/basic/index):

| Key | Required |
|---|---|
| `io.modelcontextprotocol/protocolVersion` | yes |
| `io.modelcontextprotocol/clientCapabilities` | yes |
| `io.modelcontextprotocol/clientInfo` | no (SHOULD send) |
| `io.modelcontextprotocol/logLevel` | no |

Results carry a required `resultType` (`"complete"` or `"input_required"`); an absent
`resultType` from an earlier-revision server means `"complete"`. Servers SHOULD include
`io.modelcontextprotocol/serverInfo` in each result's `_meta`.

`DiscoverResult`: `{ resultType, supportedVersions, capabilities, instructions?, ttlMs?,
cacheScope?, _meta['io.modelcontextprotocol/serverInfo'] }`.

### Version selection

**Client** takes a required `protocolVersion: ProtocolVersion | 'auto'`. A concrete revision
picks its record directly. `'auto'` probes — `server/discover` on stdio, the first request
on HTTP — and caches the resolved version for the transport's lifetime.

**Server** takes a required `protocolVersions: Array<ProtocolVersion>`. Listing both makes
it multi-version: the version is resolved per inbound request (`initialize` selects
`2025-11-25`; a `_meta` protocol-version key selects that revision), one `ContextServer` on
one transport serves both, and `server/discover` advertises exactly the configured list.

## Components

### `context-protocol`

`versions/` as above. `rpc.ts` gains `-32020` `HeaderMismatch`, `-32021`
`MissingRequiredClientCapability`, and `-32022` `UnsupportedProtocolVersion` (with
`data: { supported, requested }`), and keeps `-32002` and `-32042` as accept-only codes for
`2025-11-25` peers. `2026-07-28.ts` adds the discover request and result, the `_meta`
envelope with its required keys, and `resultType`.

Message-union validators become per-version. A server configured for both validates an
inbound message against the union of its configured versions, then resolves the version from
the message itself.

### `context-rpc`

Stays MCP-version-agnostic, which is its charter. The only change is a subtraction: the
hardcoded `ping` auto-answer at `packages/context-rpc/src/rpc.ts:208` is removed, and ping
dispatch moves to `ContextClient` / `ContextServer`, driven by the resolved protocol's method
table.

### `context-client`

- `protocolVersion` required.
- `#initialized` generalizes to a readiness promise: `2025-11-25` runs the handshake
  unchanged; `2026-07-28` resolves immediately and `_write` stops gating on it.
- Capability gating has no negotiated capabilities to read in `2026-07-28`, so
  `CapabilityNotDeclaredError` is backed by a lazily fetched `server/discover`, cached per
  client and honoring `ttlMs`. It fires only from the methods that already gate
  (`listTools`, `setLoggingLevel`, `complete`), so discover stays optional for everything
  else.
- `initialize()` remains for `2025-11-25`; `discover()` is added. Calling the one that does
  not belong to the configured version throws.
- Constructing with `createMessage`, `elicit`, or `listRoots` handlers *and* `2026-07-28`
  throws at construction (decision 5).
- A result with `resultType: 'input_required'` throws a typed error naming MRTR and B7.

### `context-server`

- `protocolVersions` required.
- Per request: resolve the version, then reject a missing required `_meta` with `-32602`, an
  unsupported version with `-32022`, and a handler needing an undeclared client capability
  with `-32021`.
- Adds the `server/discover` handler.
- Results pass through `wrapResult`.
- Logging becomes request-scoped for `2026-07-28`: the level comes from the request's
  `_meta` `logLevel`, and `notifications/message` is emitted only for requests that carried
  it — replacing the connection-wide `#clientLoggingLevel` for that version.
  `notifications/roots/list_changed` is absent from the `2026-07-28` method table.
- Caching hints become mandatory for `2026-07-28`: the spec requires `ttlMs` and
  `cacheScope` on every `complete` result of `server/discover`, `tools/list`,
  `prompts/list`, `resources/list`, `resources/templates/list`, and `resources/read`. Today
  `ServerConfig.cache` is optional and its hints reach only `tools/list` and `prompts/list`.
  They must also be merged into the resource handler results and `server/discover`, and a
  `2026-07-28` server falls back to `{ ttlMs: 0, cacheScope: 'private' }` when unconfigured
  — the conservative pair (immediately stale, no shared caching). `2025-11-25` behavior is
  unchanged: hints are emitted only when configured.
- `resources.subscribe` is never advertised for `2026-07-28`: the spec replaces
  `resources/subscribe` with `subscriptions/listen` (B4), and mokei implements neither.
- `ServerClient.createMessage` / `elicit` / `listRoots` called while serving a `2026-07-28`
  request throw the same typed MRTR error.

### `http-client`

Always sends `MCP-Protocol-Version`; `Mcp-Method` and `Mcp-Name` already ship from G2. For
`2026-07-28`: no `Mcp-Session-Id`, no `Last-Event-ID` resumption, no GET stream. Under
`'auto'`, the first request is sent in `2026-07-28` form and a `400` body is inspected — a
recognized `-3202x` error identifies a current server (retry with a supported version),
anything else falls back to `initialize`. The resolved version is cached per origin.

### `http-server`

`2026-07-28` requests skip session creation and validation entirely and ignore any
`Mcp-Session-Id`. Missing required `_meta` or headers is `400`. No GET SSE endpoint for
`2026-07-28` (`405`); the POST response stream still carries request-scoped progress and log
notifications. Origin validation and replay protection are unchanged and apply to both
versions.

### `host`

`addLocalContext`, `addHTTPContext`, and the in-process `createContext` all require
`protocolVersion`. `'auto'` resolution is cached per context config.
`packages/host/src/local-tools.ts` is unchanged — its existing `notAvailable` handlers
already cover the local-tool case.

### `session` / `agent`

Plumbing only: `protocolVersion` threads through context config. Neither layer configures
sampling handlers today, so decision 5 costs them nothing.

### `cli`

Context config gains a `protocolVersion` field defaulting to `2026-07-28`, so existing user
configs keep loading.

## Data flow — `tools/call` on `2026-07-28`

1. Client `request()` calls `decorateRequest`, injecting `protocolVersion` and
   `clientCapabilities` (plus `clientInfo`, plus `logLevel` when set) into `_meta`.
2. stdio writes the message; HTTP POSTs it with `MCP-Protocol-Version`, `Mcp-Method`, and
   `Mcp-Name` headers and no session header.
3. The server validates the inbound message, resolves the version from `_meta`, and
   dispatches the handler with the request-scoped log level.
4. `wrapResult` adds `resultType: 'complete'` and `_meta` `serverInfo`.
5. The client validates `resultType`, then runs the existing `outputSchema` check unchanged.

## Error handling

| Condition | Behavior |
|---|---|
| Missing required `_meta` on a `2026-07-28` request | `-32602`, HTTP `400` |
| Version not in the server's `protocolVersions` | `-32022`, `data: { supported, requested }`, HTTP `400` |
| Handler needs an undeclared client capability | `-32021`, `data.requiredCapabilities`, HTTP `400` |
| `x-mcp-header` schema stale | `-32020` (was `-32001`; the `SESSION_EXPIRED` collision that blocked G7 part 5 is gone — renumber only, retry stays backlog) |
| Method absent from the resolved version's table | `-32601`, even when the other configured version has it |
| `initialize` sent to a `2026-07-28`-only server | error names the supported versions, per spec |
| Result carries `resultType: 'input_required'` | typed error naming MRTR and B7 |

On `-32022`, a pinned client throws `UnsupportedProtocolVersionError` carrying the server's
list; an `'auto'` client retries once with the highest mutually supported version, then
throws.

`'auto'` probe failures — an unrecognized error or a timeout on stdio, a `400` without a
recognized `-3202x` body on HTTP — resolve to `2025-11-25` and are cached; a later failure
re-probes.

`initializeTimeout` generalizes to `setupTimeout` (same 30s default), covering both the
handshake and the probe, with the old name kept as a deprecated alias.

> **Amended (2026-08-02), after the whole-branch review.** As written this leaves a pinned
> `2026-07-28` connection with *nothing* bounded — no handshake, no probe — and
> `ContextRPC.request` arms a timer only when the caller passes `options.timeout`, so a server
> that is spawned but never writes a byte hangs its caller forever where the same server fails
> in 30s on `2025-11-25`. `setupTimeout` now also covers one `server/discover` issued at setup
> on any revision with `requiresHandshake: false`, which restores the liveness bound and seeds
> the capability snapshot the first gated call would otherwise fetch. An error *response* to
> that call is accepted — a live peer that does not implement discovery is still usable — so
> only silence fails setup.
>
> It is not free. A client whose first call is capability-gated (`listTools`,
> `complete`) pays nothing — the request setup now sends is the one that call would have sent
> anyway — and an `'auto'` client is a request *better* off, since the probe's result is no
> longer thrown away. But a client whose calls are all ungated (`prompts/list`,
> `resources/read`, `getPrompt`) now sends one request per connection it did not send before.
> That is the price of the bound, and it is worth paying: the alternative is a host that hangs
> forever on a server that never answers.

## Testing

1. **Regression gate first.** Every existing suite passes untouched with `2025-11-25` passed
   explicitly. A behavior change on the `2025-11-25` path is a bug in this slice.
2. **Conformance fixtures** in `packages/context-protocol/test/conformance/`, run per
   version: envelope required-field rejection, `resultType` present and absent-means-complete,
   discover result shape, and each new error code's `data` payload.
3. **Unit tests** per package: protocol-record hooks, request-scoped log level, absence of
   the session header on `2026-07-28` HTTP, method-table gating of `ping`, and mandatory
   caching hints on all six cacheable operations including the unconfigured-server fallback.
4. **Interop matrix** against SDK `2.0.0`, extending `integration-tests/support/interop/`:
   mokei client ↔ SDK server and SDK client ↔ mokei server, each over stdio and HTTP, on
   `2026-07-28` — reusing the shared expectations the `2025-11-25` suites already assert
   (`tools/list` including `outputSchema`, `tools/call` text and `structuredContent`,
   prompts, resources), plus `server/discover`.

   > **Amended (2026-08-01).** During plan 1 this branch concluded that SDK `2.0.0` does not
   > implement `2026-07-28` and that no peer existed to test against, and wrote that conclusion
   > into both plans and the stdio interop suite. **It is false.** SDK `2.0.0` ships executable
   > support for the revision — `FIRST_MODERN_PROTOCOL_VERSION = "2026-07-28"`,
   > `MODERN_WIRE_REVISION`, `SUPPORTED_MODERN_PROTOCOL_VERSIONS`, `isModernProtocolVersion()`,
   > a wire codec, `validateEnvelopeMeta()` and a `server/discover` handler.
   > `LATEST_PROTOCOL_VERSION = "2025-11-25"` is true, but it names only what the *handshake*
   > negotiates, and `2026-07-28` has no handshake.
   >
   > **Both sides implement it, so this matrix is reachable in full.**
   >
   > - **Server side:** `createMcpHandler` (public export) over Streamable HTTP; `serveStdio`
   >   over stdio, which also accepts `{ legacy: 'reject' }` to serve `2026-07-28` and nothing
   >   else (`server/dist/stdio.d.mts:20,61`).
   > - **Client side:** `new Client(info, { versionNegotiation: { mode: { pin: '2026-07-28' } } })`
   >   — a documented, public `ClientOptions` field
   >   (`client/dist/index.d.mts:1665`, `VersionNegotiationMode` at `:1583-1586`), backed by the
   >   same runtime constants in the client bundle.
   >
   > All four quadrants were driven against mokei with **zero mokei changes**: mokei client →
   > SDK server over stdio and HTTP, and SDK client → mokei server over stdio and HTTP. Each
   > completed `tools/list` and `tools/call`.
   >
   > What actually *shipped as a suite* is one quadrant — **mokei client ↔ SDK server over
   > HTTP**, in `interop-2026-07-28-http.test.ts`. The other three are reachable through
   > documented public options and were simply not built. The nearest next step — pointing
   > `checkMokeiClient` at the SDK peers for `2026-07-28` — is tracked in
   > `docs/agents/plans/backlog/2026-06-20-mcp-draft-remaining.md`.
5. **Version-detection cases** from the spec's compatibility matrix: an `'auto'` client
   against a `2025-11-25` server falls back; a `2025-11-25` client against a multi-version
   server works; a `2026-07-28`-pinned client against a `2025-11-25` server fails
   deterministically with an actionable error.

## Risks

- **Dual-path test matrix doubles.** Mitigated by a single public handler surface, one
  branch point per seam, and table-testing both versions against shared expectations.
- **Breaking API change.** `protocolVersion` becomes required across the core packages.
  Acceptable at 0.x; needs a changeset and migration note.
- **Probe ambiguity on stdio.** A `2025-11-25` server has no standard negative response to
  `server/discover`, so `'auto'` leans on a timeout. Explicit pinning stays the recommended
  configuration; the probe is best-effort and its result is cached.
- **Capability gating via lazy discover** adds a request that the spec calls optional. Scoped
  to the three methods that already gate, and cached per `ttlMs`.
