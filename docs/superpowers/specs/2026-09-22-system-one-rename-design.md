# System One rename -- design

Date: 2026-09-22
Branch: `feat/laya-classification`
Status: design approved

## Purpose

The classification packages built on this branch are named after Laya, but Laya is one model family
and one runtime (`laya.cpp`) behind a more general contract: the TypeSafe System One API, a
typed-question classification interface (`POST /v1/systemone`). Name the packages and public API
after the generic contract, and keep the Laya name only for code that is genuinely `laya.cpp`
specific. This keeps the client honest about what it speaks and leaves room for other System One
runtimes (the hosted TypeSafe API today, an in-process ggml backend later) without a Laya-branded
surface.

## Constraints

- Both packages are unreleased; the branch is unmerged. The rename is clean: no deprecation
  aliases, no compatibility re-exports.
- Naming only. Wire contract, runtime behavior, test coverage, and package version (`0.13.1`) do not
  change.
- Laya survives only on `laya.cpp`-specific pieces. No exported type carries the Laya name after
  the rename.
- `@mokei/system-one-client` stays platform-neutral (no `node:*` imports), as before.

## Rejected alternative

Merge the branch first, rename on a follow-up branch. Rejected: it lands Laya names on `main` and
churns history for no benefit, since nothing has been published.

## Packages and paths

| Before | After |
|--------|-------|
| `packages/laya-client`, `@mokei/laya-client` | `packages/system-one-client`, `@mokei/system-one-client` |
| `mcp-servers/laya`, `@mokei/mcp-laya` | `mcp-servers/system-one`, `@mokei/mcp-system-one` |
| bin `mcp-laya` | bin `mcp-system-one` |
| MCP server name `laya` | `system-one` |
| `mcp-servers/config.json` key `laya` | `system-one` (args path follows the directory) |
| `pnpm-workspace.yaml` `versioning.fixed` entries | renamed to the new package names |

Directories move with `git mv` so history follows. `pnpm-lock.yaml` is regenerated by
`pnpm install`; afterwards `pnpm install --frozen-lockfile` must report up to date.

Package descriptions become "Mokei System One classification client" and "System One
classification MCP server"; the manifest display name becomes "Mokei System One". Package
`keywords` gain `system-one` and keep `laya`, since Laya is a supported runtime and the keyword aids
discovery.

already generic do not change.

names, and test descriptions follow the same rule.

## Public API: MCP server package

| Before | After |
|--------|-------|
| `createLayaConfig` | `createSystemOneConfig` |
| `createLayaTools` | `createSystemOneTools` |
| `LayaServerTypes` | `SystemOneServerTypes` |
| `LayaToolsOptions` | `SystemOneToolsOptions` |
| env `LAYA_URL` | `SYSTEM_ONE_URL` |
| env `LAYA_API_KEY` | `SYSTEM_ONE_API_KEY` |
| env `LAYA_MODEL` | `SYSTEM_ONE_MODEL` |

The default URL stays `http://localhost:8000`. Tool names (`predict`, `route`, `guard`, `moderate`,
`triage`) do not change. Tool and schema descriptions say "System One" where they said "Laya"
(for example "Classify text with System One typed questions (choice/score/noul)").

## Where Laya survives

Only `laya.cpp`-specific pieces keep the name:

- The `batch` option's JSDoc and the docs describe `POST /v1/decide/batch` as a `laya.cpp`
  extension absent from the hosted API.
- The reference doc's local-backend section covers running `laya serve` (ggmlc binary) and
  compiling a Laya GGUF.
- The backlog item for the future in-process ggml / `laya.cpp` backend (`laya-ggml-*` packages)
  keeps its Laya name, re-pointed at `SystemOneBackend`.
- Model-family names used as examples (for example the `english` GGUF) stay as they are.
- Package `keywords` keep `laya`.

## Docs

- `docs/reference/laya-sidecar.md` becomes `docs/reference/system-one-sidecar.md`. It leads with
  the generic System One contract, then describes the backends: `laya.cpp` (`laya serve`, local)
  and the hosted TypeSafe API. Code samples and env vars use the new names.
- The completed summary `docs/agents/plans/completed/2026-09-22-laya-classification.complete.md`
  becomes `2026-09-22-system-one-classification.complete.md`, rewritten with the new names. It
  records Laya as the first supported runtime and notes the rename as a design decision.
- `docs/agents/plans/backlog/2026-09-22-laya-in-process-ggml-backend.md` keeps its name; its
  references move to `SystemOneBackend`, `@mokei/system-one-client`, and the renamed completed
  summary.

## Verification

- `@mokei/system-one-client` and `@mokei/mcp-system-one` tests pass with the same test counts as
  before the rename (37 and 4).
- Both packages build; `pnpm test:types` and `rtk proxy pnpm run lint` are clean; the full
  `pnpm test` suite passes (the known `context-client` ack-timeout timing flake excepted, confirmed
  by a retry).
- `pnpm install --frozen-lockfile` reports up to date.
- `git grep -i laya -- ':!docs/superpowers' ':!pnpm-lock.yaml'` returns only the survivors listed
  above plus the completed summary's mentions of Laya as the first runtime.

## Out of scope

- Any behavior, wire, or schema change.
- The in-process ggml / `laya.cpp` backend itself.
